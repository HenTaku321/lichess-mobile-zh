# 象棋集成交互审查与整改

## 目标与执行约束

基准是同一版本的 Lichess App；保留象棋规则、九路十行和现有棋子材质。
按棋盘/对局、分析/复盘、其他页面三批推进，区分源码发现、运行复现和验收。
Flutter 测试、分析、codegen 和编译使用 GitHub Actions，不在本机编译，不开子代理。
本机可做格式/diff 检查，并运行既有 Linux 二进制；运行检查使用隔离的测试配置。

## 已确认的审查基线

源码和已发布 Linux 包均对应 `34024fcff`；该提交的全量 Tests 和 Linux 构建已通过。
既有回归没有 golden、逐页截图或移动端声音/触觉验收，因此不能声明全量 UI 一致。
象棋 REST 和 Socket 直连 xiangqi.com；其业务逻辑在 Dart controller/repository/network 层，
相邻 Go 服务主要处理 Lichess 翻译代理，不作为象棋上游服务源码。

## 第一批实施步骤

1. 新增 `xiangqi_history_parity_test.dart`，通过假 transport 驱动真实页面，再执行长按手势。
2. 在独立分支的 Actions 中验证失败确实是上述差异，而非 fixture 或加载失败。
3. 复用已有 `RepeatButton` 和 `BottomBarButton`，统一 tooltip、禁用态和历史按钮标签。
4. 在线重复动作读取当前 cursor；轮到我方时显示返回实时局面的提醒；浏览不得发出走子。
5. 检查抵达两端、松手、实时帧到达和页面销毁后的定时器与状态，不改动真实对局历史。
6. 通过分组及全量回归后，才交付本批结果；后续批次继续追踪动画、反馈和复盘数据。

### 首批进展与复盘契约红回归

Actions `40800187762`（源码 `e291c5337`）：原有专项及首批历史浏览共 77 个通过，新增
复盘契约 6 个失败。四页长按都已通过；返回实时局面的提醒使用真正的 `turn == mySide`，
不能使用同时要求“已在实时位置”的 `isMyTurn`（后者是走子权限，不是回放提示的条件）。

复盘评估条晚一手、零步归档 `No element`、不完整分析 `RangeError`、非法评分当成中性、
黑方先走的归属和翻转缺失均在真实 repository + 假 transport 的页面测试中复现。
原始抓包尾部的连续将杀评分 `3, -2, 2, -1, 1, 0` 证明其评分采用走棋方视角，和已捕获
客户端的 `100 - nextWinRate` 计算一致；历史 `docs/review.md` 的“红方视角”文字不能覆盖
这些证据。`mate: 0` 仍需要通过当前局面的走棋方判断失败方，普通整数正负无法保留 `-0`。

Actions `40801534539`（源码 `4ae9c957f`）：77 个通过、7 个失败；构造的合法一步将杀局面
已经被规则引擎识别为将死，但制胜着的准确率实际为 `1`（期望 `100`）。这确认了
`mate: 0` 丢失失败方信息，而不是仅仅一个分数文字显示问题。

复盘修复在内部模型中保存每个局面的完整评分（含末局面），保留 `ply` 从零开始，同时
记录初始走棋方。上游请求和回复形状不变；没有 secure-storage 或数据库迁移。
坏分数和评分数量不完整在 repository 层失败，不能生成一个会越界的“成功”复盘。
